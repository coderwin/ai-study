# MCP 질문과 답변

대화에서 나온 내용을 질문·답변으로 정리했다. 답변은 각 5줄이다.

## Q. MCP가 뭔가요?

MCP는 Model Context Protocol이고, AI 앱이 외부 도구·데이터에 붙는 오픈 표준이다.  
Cursor 같은 클라이언트가 MCP 서버에 연결해 Slack, 캘린더, DB 같은 기능을 쓴다.  
모델이 세상과 직접 말하는 규격이 아니라, 중간에 통하는 플러그 규격이다.  
목적은 토큰 절약보다 AI에게 정해진 기능을 주는 것이다.  
USB처럼 한 번 만들면 여러 AI 앱에서 재사용할 수 있다.

## Q. MCP는 AI나 내가 외부 API를 간편하게 쓰는 방법이고, Slack·캘린더에 기록할 수 있나요?

핵심은 맞다. 다만 일상적으로 API를 치는 주체는 당신보다 Agent다.  
당신은 채팅으로 시키고, AI가 MCP 도구를 고르며, 서버가 실제 API를 호출한다.  
Slack 메시지, 캘린더 일정처럼 쓰기도 되고 조회·수정도 된다.  
MCP 자체가 Slack API는 아니고, 그 API를 감싼 서버가 있어야 한다.  
외부 HTTP API뿐 아니라 로컬 파일, DB, 브라우저에도 붙을 수 있다.

## Q. 도구가 뭔가요?

도구는 AI가 누를 수 있게 미리 만들어 둔 기능 버튼이다.  
이름과 채워야 하는 칸(인자)이 있다.  
예는 `메시지_보내기(채널, 내용)`이다.  
AI는 Slack 문서를 읽고 HTTP를 짜는 게 아니라 이 버튼을 호출한다.  
식당 주문서에 메뉴와 옵션을 적는 일과 같다.

## Q. “서버가 공개한 도구 이름과 인자를 호출한다”는 무슨 뜻인가요?

AI가 보는 것은 Slack REST 문서가 아니라, MCP 서버가 알려 준 도구 목록이다.  
그래서 `메시지_보내기`처럼 정해진 이름과 인자만 보낸다.  
URL, 헤더, OAuth 같은 HTTP 상세는 모델이 만들지 않는다.  
그 상세는 서버 코드가 알고 있다.  
당신은 리모컨 버튼만 누르고, 실제 TV 신호는 리모컨이 만드는 것과 같다.

## Q. MCP 서버는 MCP를 제공하는 업체 서버인가요?

항상 그렇지는 않다. MCP 서버는 MCP 말을 알아듣는 프로그램이면 된다.  
업체가 만든 것, 커뮤니티가 만든 것, 내가 만든 것이 있다.  
내 PC에서 실행될 수도 있고 클라우드에 있을 수도 있다.  
Slack 본사 서버는 그 뒤에 따로 있고, MCP 서버는 앞에 앉은 통역사에 가깝다.  
로컬이면 Cursor가 내 PC에서 프로세스를 띄우고, 원격이면 URL로 바깥 서버에 붙는다.

## Q. 결국 외부 API 호출 아닌가요? API 없이도 소통되나요?

Slack에 메시지를 남기려면 어딘가에서는 Slack API가 필요하다.  
다른 점은 그 API를 AI가 아니라 MCP 서버가 친다는 것이다.  
AI와 MCP 서버 사이는 Slack API가 아니라 MCP로 이야기한다.  
파일 저장, 로컬 DB처럼 외부 API가 필요 없는 MCP도 있다.  
마법으로 기록이 생기는 것은 아니다.

## Q. 이러면 토큰도 줄일 수 있나요?

REST 문서를 모델에게 먹이고 `curl`을 짜게 하는 방식보다 줄어들 수는 있다.  
MCP의 본래 목적은 토큰 절약이 아니다.  
도구 설명은 대화 입력에 들어가고, 서버를 많이 켜면 오히려 늘어난다.  
도구 결과가 큰 JSON이면 컨텍스트가 커진다.  
절약은 있을 수도 있는 부작용이다.

## Q. MCP 서버의 Slack POST는 AI가 도구로 호출하는 것 아닌가요?

아니다. 호출은 두 번이다.  
AI는 MCP 서버에 `메시지_보내기(채널, 내용)`만 보낸다.  
Slack `POST /chat.postMessage`는 그다음 MCP 서버 프로그램이 실행한다.  
느슨히 “AI가 도구로 슬랙에 보냈다”는 맞다.  
딱 말하면 AI가 호출한 것은 Slack API가 아니라 MCP 도구다.

## Q. 메시지를 보낼 수 있는 MCP 서버가 내 컴퓨터에서 실행되나요?

로컬 MCP라면 그렇다. 원격 MCP라면 바깥 서버에서 실행된다.  
어느 쪽이든 메시지 본문은 Slack 회사 서버에 저장된다.  
내 컴퓨터가 Slack이 되는 것은 아니다.  
Cursor 설정에서 `command`면 로컬, `url`이면 원격인 경우가 많다.  
로컬이든 원격이든, 도구를 받아서 Slack에 POST 하는 쪽이 MCP 서버다.

## Q. (로컬) Slack MCP 서버는 내 PC에서 도나요?

맞다. Cursor가 내 PC에서 Slack MCP 프로그램을 실행한다.  
AI의 도구 호출은 같은 PC 안의 그 프로세스가 받는다.  
그 프로세스가 인터넷으로 Slack API에 POST를 보낸다.  
메시지는 Slack 클라우드에 남는다.  
Cursor가 자식 프로세스로 띄우는 작은 프로그램에 가깝다.

## Q. 켜 두면 계속 구동되고 메모리도 많이 차지하나요?

Cursor에 연결되어 켜 둔 동안에는 대기 프로세스로 살아 있다.  
할 일이 없으면 Slack을 계속 두드리는 게 아니라 기다린다.  
Cursor나 MCP를 끄면 같이 끝나는 경우가 많다.  
Slack 같은 API 래퍼는 보통 가볍다.  
메모리를 크게 쓰는 쪽은 대개 Cursor, 브라우저, 언어 서버다.

## Q. API 래퍼 MCP는 로컬 서버 안에 API를 호출하는 함수가 있다는 뜻인가요?

맞다. 겉은 MCP 도구이고, 속은 기존 API를 치는 함수다.  
AI는 `메시지_보내기`를 부르고, 서버 함수가 `chat.postMessage`를 호출한다.  
Slack API를 새로 만든 것이 아니다.  
이미 있는 API를 MCP 서버가 감싸서 대신 치는 형태다.  
그래서 이름이 API 래퍼(wrapper)다.

## Q. 대화창에서 “호출해줘”라고 하는 것과 뭐가 다른가요?

말만 하면 설명이나 `curl` 예시가 나올 뿐, 실제 API는 안 나간다.  
MCP면 그 말이 등록된 도구 호출로 바뀌고, 서버가 API를 실행한다.  
대화창의 문장은 의도이고, MCP 도구 호출이 실행이다.  
Cursor Agent가 터미널에서 코드를 짜서 돌리면 그건 스크립트 방식이다.  
채팅 문장 자체가 Slack 요청은 아니다.

## Q. 호출용 API·자동 스크립트를 만들어 AI가 실행하는 것과 차이가 있나요?

있다. 스크립트도 실제로 Slack에 보낼 수 있다.  
차이는 AI가 매번 코드를 즉흥으로 짜느냐, 미리 있는 버튼만 누르느냐다.  
스크립트는 형식·인증·에러 처리가 대화마다 달라질 수 있고 터미널 권한이 넓다.  
MCP는 도구 이름과 인자가 고정되고, 실행 범위가 `메시지_보내기`처럼 좁다.  
한 번만 쓸 작업은 스크립트가 단순하고, 반복해서 쓸 기능은 MCP가 맞다.

## Q. 사용 이유는 코드 없이 외부 작업을 처리하고, 한 번만 설정하면 어디에서나 쓰는 것인가요?

맞다. 쓰는 이유는 코딩 없이 말로 외부 일을 시키기 위해서다.  
클라이언트에 한 번 붙여 두면 그 안에서는 계속 재사용할 수 있다.  
같은 Cursor에서 전역으로 켜 두면 프로젝트·채팅이 바뀌어도 다시 쓸 수 있다.  
다른 AI 앱이나 다른 PC에는 같은 규격이어도 연결 설정을 한 번 해야 한다.  
프로젝트 전용으로만 넣어 두면 그 폴더 안에서만 보인다.
